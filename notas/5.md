## Building and testing FigCraft headless on Linux: what I found

I made no changes to the repo and ran no cargo commands in it. Everything below comes from reading files, grepping, and looking at the build another agent was already running.

### 1. Toolchain and configuration
- **No `rust-toolchain(.toml)` file.** CI uses `dtolnay/rust-toolchain@stable` with clippy and rustfmt (`.github/workflows/ci.yml:44-46`). The workspace sets `edition = "2024"` and `rust-version = "1.95"` (`Cargo.toml:10,12`).
- **This container has:**
  - rustc and cargo 1.97.0, clippy, rustfmt.
  - Only the `x86_64-unknown-linux-gnu` target. **There is no `wasm32-unknown-unknown`**, so the wasm step of `cargo xtask ci` fails until someone runs `rustup target add wasm32-unknown-unknown`.
  - crates.io is reachable (HTTP 200).
- **Formatting:** `rustfmt.toml` sets `max_width = 150`, `use_small_heuristics = "Max"`.
- **`clippy.toml`:** tests may unwrap, expect and panic (`allow-unwrap-in-tests`, `allow-expect-in-tests`, `allow-panic-in-tests`), and `too-many-arguments-threshold = 10`.
- **Workspace lints (`Cargo.toml:81-96`):**
  - `unsafe_code = "forbid"`.
  - clippy `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented` and `unreachable` are all `deny`.
  - `dbg_macro = "warn"`.
- **Profiles:** dev builds use `opt-level = 1`, dependencies `opt-level = 2` (`Cargo.toml:98-102`).
- **`.cargo/config.toml`** sets `CRAFT_FONTS_DIR = { value = "../craft-fonts", relative = true }` and the alias `xtask = "run -q -p xtask --"`.
  - Here that path resolves to `scratchpad/craft-fonts`, which exists (97 MB). Local builds therefore embed fonts by default.
  - CI builds without the fonts (`ci.yml:60-61`).

### 2. `crates/text/build.rs` and `CRAFT_FONTS_DIR`
- The fonts are optional:
  - When `CRAFT_FONTS_DIR` is unset, `CRAFT_FONTS` is empty and the app uses system fonts (`build.rs:1-3,12-31`).
  - When a manifest is missing, the build only warns (`build.rs:24,27-28`). It becomes a hard `cargo::error` only if `CRAFT_FONTS_REQUIRED` is set (`build.rs:21-22`).
  - CJK fonts are embedded only with `FIGCRAFT_EMBED_CJK` (`build.rs:63-66`).
- If craft-fonts appears after a first build, run `cargo clean -p figcraft-text` (README.md:254).
- CLAUDE.md:51-54: "Everything must build, test and run without it (system fonts are scanned at runtime)."
- The concurrent build uses `CRAFT_FONTS_DIR=$S/craft-fonts CRAFT_FONTS_REQUIRED=1`; its generated `craft_fonts.rs` has 56 `include_bytes!`.
- To reproduce CI exactly, point `CRAFT_FONTS_DIR` at a path that doesn't exist. A shell variable overrides cargo's `[env]` when `force` isn't set.

### 4. How long a build takes (measured from the build already running)
- The other agent ran `nice -n 10 cargo test --locked -p figcraft-ui-egui -p figcraft-engine --no-run -j 2` with craft-fonts and debuginfo=2 (`-C debuginfo=2` on its rustc command line), starting from an empty target dir:
  - started 14:32:50
  - `figcraft_ui_egui` test binary ready at 14:52:02 (914 MB)
  - `figcraft_engine` test binary ready at 14:53:41 (808 MB)
  - **about 21 minutes in total; the target dir grew to 8.8 GB.**
- **Desktop app dependencies are not downloaded yet.** The registry cache holds 218 crates out of 588 locked packages, with no eframe, wgpu or winit. The first `cargo build -p figcraft` or `cargo test --workspace` has to download and compile wgpu and winit on top of that.
- **Estimate (not measured):** a cold full workspace test plus clippy `--all-targets` at `-j 4` would likely take 30-45+ minutes.
- After editing only `present.rs`, a rebuild recompiles just the ui-egui lib and its test binary. I'd guess a few minutes.
- **Disk:** 16 GB free on `/`. A second full target dir with debuginfo=2 could fill it. CI's `CARGO_PROFILE_DEV_DEBUG=line-tables-only` shrinks artifacts.
- CLAUDE.md:104-105: "Parallel agents: separate `CARGO_TARGET_DIR` per agent, edit only the crates/files you own, write manifests atomically, delete your target dir when done (disk is limited)."
- The other agent's target dir is `scratchpad/figcraft-target`, and that build had finished by 14:53:41.

### 5. Linux system dependencies
- **CI installs** `libxkbcommon-dev libwayland-dev libx11-dev libxrandr-dev libxi-dev libgl1-mesa-dev libgtk-3-dev` (`ci.yml:37-42`).
- **The desktop app** is eframe with wgpu, accesskit, wayland and x11 (`apps/figcraft/Cargo.toml:20`), using `Renderer::Wgpu` (`apps/figcraft/src/main.rs:188`). `WGPU_BACKEND` overrides the backend (`apps/figcraft/src/graphics.rs:9`).
- **The lock file suggests few `-dev` packages are needed:**
  - rfd 0.17 has no gtk-sys and uses wayland-* (`Cargo.lock:3754-3777`).
  - wayland-sys pulls `dlib`, i.e. dlopen (`Cargo.lock:5088-5097`).
  - This is unverified, because the desktop app hasn't been built here.
- **The container has:**
  - pkg-config files for x11 and fontconfig only. xkbcommon, wayland-client, xrandr, xi, gl and gtk+-3.0 `.pc` files are missing.
  - Runtime libraries libX11, libXcursor, libXrandr, libXi, libxkbcommon.so.0, libwayland-client.so.0, libGL/GLX, libvulkan.so.1 and Xvfb/xvfb-run.
- **Missing to run the app:**
  - `libxkbcommon-x11-0`, which winit on X11 loads.
  - libEGL (`libegl1`, `libegl-mesa0`). wgpu's GL backend on Linux uses EGL.
  - 64-bit lavapipe. Only `mesa-vulkan-drivers:i386` is installed.
- apt has candidates for all of them: `apt-get install -y mesa-vulkan-drivers libegl1 libegl-mesa0 libxkbcommon-x11-0`. Then `xvfb-run -a -s "-screen 0 1600x1000x24" cargo run -p figcraft -- --control <port>`.

### 6. Tests that cover the presenter and player, and how they drive it
**The harness is headless egui, with no window and no GPU.**
- `crates/ui-egui/src/present_tests.rs:12-71` defines `Ui { ctx: egui::Context::default(), app: FigApp::new(s, Box::new(NoServices)), time }`.
  - Each `frame(events)` calls `ctx.run_ui(RawInput{screen_rect 1440×900, time += 1/60, events}, |ui| app.ui(ui))` (:25-31).
  - `run(cmd, params)` executes an engine command, calls `handle_ui_requests()`, then draws one frame (:39-44).
  - `pane()` reads the pane's area rect from `ctx.memory` (:47-49).
  - `preview()`/`scroll_y()` read `app.inspect()["preview"]` (:52-58).
  - `button()`/`key()` inject `Event::PointerButton`/`Event::Key` (:60-70).
- **Simulated input:** `Event::PointerMoved`, `PointerButton`, `Key` and `MouseWheel { unit: Point, delta, phase: Move }`. Wheel scrolling is tested at present_tests.rs:141-155, drag scrolling and rubber-banding at :156-171.
- **What the tests assert on:** the player's state as JSON, `Presenter::inspect()` (present.rs:570-603).
  - Fields: current, scroll, scrollRange, viewport, scale, zoom, pan, panRange, hotspots (screen rects), responsive, frameSize, flinging…
  - Exposed through `FigApp::inspect()` as `presenter`, `presentOptions` and `preview` (lib.rs:1149-1151).
  - **There is no field for the on-screen rect of the presented frame.** Hotspot rects or pan/panRange stand in for it.

**Test files:**
- `present_tests.rs` (3 tests): pane opens and follows edits; wheel and drag scrolling; full-window presenter, Escape, control channel.
- `present_view_tests.rs` (8 tests):
  - Scale options cycle with Z (:80-95).
  - `presenter_scales_by_its_options_and_pans_what_overflows` (:117-177) asserts zoom, panRange and pan per scale, including "100%: both ways overflow, centred across at the top", `pan == [312, 0]` (:135-140). This is a template for a left-alignment or centring regression test.
  - Device rotation, fling momentum and wheel coasting (:212-278).
- `present_behaviour_tests.rs` (12 tests, gestures through the same harness; :1-125) — submodule `present::behaviour_tests` (`present.rs:2672`).
- `present_tail_tests.rs` (5) — `present::tail_tests`; uses a `FakePads` Services mock (:46).
- `present_delay_tests.rs` (4) — `present::delay_tests`.
- `present_variables_tests.rs` (3) — `present::variables_tests`.
- Unit tests inside `present.rs` (`mod tests`, from :2683).
- `proto_responsive_tests.rs` (5).
- `proto_editor_tests.rs` (hotspot flash and the presenter's inspect panel).
- Engine side: `crates/engine/src/proto_*_tests.rs` (behaviour, present, responsive, run, tail, delay, …).
- **Gap:** no test clicks the presenter's top bar or its Options menu. `top_bar` is at present.rs:2046 and `options_menu` at :2160. Grepping the tests for "Options" or `BarAction` finds nothing.

### 9. Localization: UI strings are translated
- **Mechanism:** `crates/ui-egui/src/i18n.rs` provides `tr`, `trf`, `trn` (:105-124), plus `tr_noop`. Catalogs are `crates/ui-egui/locales/{en,es,es-419,fr,de,pt-BR,ja,ko,zh-Hans}.toml`, baked in by `crates/ui-egui/build.rs:11-12,36-72`.
- **The rule, verbatim (docs/translating.md:85-89):** "Wrap every string a user sees or a screen reader hears: `tr` for plain text, `trf` for `{named}` placeholders, `trn` for counts, `tr_noop` for literals in `const` tables that are looked up later with `tr(label)`. The key must be a string literal as the first argument (the check reads the source). … Then add the key to `en.toml` and to each complete language (Spanish); the drafts may follow later."
- `COMPLETE = ["es"]` (i18n_tests.rs:9). The i18n test fails on:
  - keys the code uses that `en.toml` lacks
  - keys no code uses
  - placeholders that don't match English
  - untranslated Spanish

  (docs/translating.md:78-81)
- **In practice every draft is kept at 100%.** docs/localization-parity.md:47-48: "Every draft translates every string as of 2026-10-12", and the revision rows are "drafts catch up" passes. The user writes Portuguese, so adding pt-BR too is sensible.
- **The presenter already follows this pattern:**
  - Scale labels: `tr("Fit width")`, `tr("Actual size (100%)")`, `tr("Responsive")`… (present.rs:175-181, 2165-2201).
  - Bar buttons: `tr_noop("Close")`, `tr_noop("Options")`… then `tr(label)` (present.rs:2068-2085).
- **Keys that already exist:** "Actual size (100%)" en.toml:31 (es "Tamaño real (100%)"), "Copy link" en.toml:307, "Fit width" en.toml:500, "Responsive" en.toml:1085, "Share" en.toml:1176, each with es and pt-BR translations.
- **Not found as exact keys:** "Share prototype", "Fit width and height", "Fill screen", "Advanced settings", "Hide UI", "Get embed code", "Anyone can view", "Who has access". These need adding to en.toml and es.toml at least.
- **New command labels** need Spanish under `[commands]` (docs/translating.md:25-28).
