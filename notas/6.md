## Completeness check: the claims the design depends on, checked against the code

Repo root: `/tmp/claude-0/-home-user/e91b1203-da4e-5e42-9cdb-6a036b7511c0/scratchpad/figcraft`. I only read files. I modified nothing and ran no cargo command. All paths below are relative to the repo root.

### Part 1. The six claims I checked by opening the cited lines

**1. Where the frame's position on screen is computed (centred or left)** — CONFIRMED
- `layout()` is at `crates/ui-egui/src/present.rs:1528-1592`.
- `excess` is computed at 1568-1569 and becomes `pan_range` at 1570.
- The pan is clamped only when no drag or fling is moving the view (1571-1575).
- The placement on each axis is:
  ```rust
  let along = |excess, min, centre, len, pan| if excess > 0.0 { min - pan as f32 } else { centre - len / 2.0 };
  ```
  (1577-1578). The frame is then placed with `Place::centered(fb, screen.center(), scale)` (1580; `Place::centered` is at 952-955).
- The view's pan comes from `offset(View) = self.pan.unwrap_or((self.pan_range.0 / 2.0, 0.0))` (397). So the frame is centred horizontally only while `pan` is `None`.
- The first wheel scroll, drag or fling stores an absolute value: `Scroller::View => self.pan = Some(v)` (420). Any x is clamped to 0 while `pan_range.0 == 0` (1574).
- `pan` is reset only in three places: `set_scale` (389), `go` (649) and `restart` (672). `sync` (446-480) never resets it, and neither does a change of window size.
- Once there is horizontal excess, the frame starts at `avail.min.x - 0`, i.e. at the left edge.

**What the defaults mean for the left-alignment bug** (new, from the code)
- A new page has `device: "None"` and `responsive: false` (`crates/doc/src/proto.rs:826-837`).
- The default scale is `Fit` (`present.rs:139-141`, 208-212).
- Fit takes `min(kx, ky)` capped at 1.0 (1552, 1563), so `excess` is always 0 and the frame always takes the centred branch.
- FitWidth also never has horizontal excess, since `scale = kx`.
- So with the defaults the frame can't end up on the left. Left alignment needs one of these non-default states:
  - **(A1)** Actual or Fill, after a scroll or drag, followed by narrowing the area: a window resize, F to leave fullscreen, or opening the Inspect panel (`Panel::right`, 1643-1650).
  - **(A2)** Responsive with no device. `respond_to(Some(whole_area))` (1531-1533) resizes **both** width and height through `figcraft_engine::cmd::proto::respond` (`crates/engine/src/cmd/proto.rs:231-244`). Children with Left constraints stay on the left.
  - **(A3)** A device narrower than the frame:
    - `viewport()` is `min(frame, device)` (`present.rs:1269-1273`);
    - `fit_viewport` keeps the content where it is (1279-1306);
    - the result is that only the left part of the design shows.
- Responsive is a file setting (`present.rs:1680`, `app.run("proto.settings", {responsive})`), so once it is on it stays on.

**2. How scroll input is routed** — CONFIRMED, including the "stalled coast" defect
- The wheel delta is `i.smooth_scroll_delta` (2253). It is used only when the pointer is over the area (2268).
- The targets are `scrollers_at` (2210-2221; frames with `overflow != None` and a non-zero range, innermost first), then `Scroller::View` if `pan_range != 0` (2301-2304).
- The whole 2D delta goes to the first target that moves, then the loop stops (`break`, 2306-2316).
- A wheel coast is created inside `input()` at 2324-2329. `step_fling` runs *before* `input()` (1989-1991) and is the only place that requests a repaint for a fling.
- egui wants another frame only for pointer movement, events, or more than 0.2 of unprocessed wheel delta (`~/.cargo/registry/src/*/egui-0.36.2/src/input_state/mod.rs:655-664`).
- **So the coast does not start until the next input event.** This is confirmed by reading the code, not by reproducing it.
- A frame scroll bumps `rev` (417). `rev` is part of the texture key (914), so the whole frame is rendered again on the CPU with `render_node_at` (921), synchronously.
- `revert()` restores `self.scroll = t.snap.scroll` (688), and the snapshot includes `scroll` (605-613). This confirms S7: leaving a "while hovering" state puts the scroll back.
- A drag picks its scroller at press time, with no check of direction (2423-2431). This confirms S6.

**3. Whether a frame can scroll at all** — CONFIRMED
- `scroll_range_in` returns `(0,0)` when `overflow == Overflow::None` (1158-1161). `Overflow` defaults to `None` (`crates/doc/src/proto.rs:751-758`).
- With the default Fit and no device, a tall page is shrunk until it fits (`pan_range = 0`). Nothing scrolls unless an inner frame has overflow set.

**4. What the server can serve over HTTP** — CONFIRMED: only `/healthz`
- `health_check` (`crates/collab-net/src/hub.rs:686-725`) peeks at the request line and answers only a `GET` whose path ends in `/healthz`, with a hard-coded `200 ok` (722).
- Everything else goes to `tungstenite::accept_hdr_with_config`. If the handshake fails, the socket is closed (`hub.rs:857-864`). There are no static files, no HTML and no viewer.
- `packaging/server/Caddyfile:8-10` sends the whole host to `reverse_proxy 127.0.0.1:47900`.
- `packaging/web/README.md:80-96` already has an iframe embed snippet (`allow="fullscreen; clipboard-read; clipboard-write"`).

**5. Whether figcraft-web can open a file from a URL or code and start in present mode** — CONFIRMED: NO
- `apps/figcraft-web/src/web.rs` reads only `location.search()`, using `query().contains("webgl")` (24, 57-59). It never reads `location.hash`.
- It always builds `Session::new()`, which creates one "Untitled" document (`web.rs:38`; `crates/engine/src/lib.rs:697-701`). `Session::empty()` exists at `lib.rs:704`.
- `web-sys` features cover Window, Document, Element, HtmlCanvasElement, Location, MediaQueryList, Navigator and Gamepad* only (`apps/figcraft-web/Cargo.toml:28`). There is no Clipboard, History or UrlSearchParams.
- `WebServices` does not implement `clipboard_set_text`; the trait's default is a no-op (`crates/ui-egui/src/lib.rs:178`). So Copy link copies nothing in the browser. egui 0.36.2 does have `Context::copy_text` (`egui-0.36.2/src/context.rs:1686`), and the repo never calls it.

**What does already work, so a bootstrap only needs glue code:**
- The browser `NetLink::join` accepts `wss://` links and codes (`crates/collab-net/src/web.rs:170-189`). It refuses `ws://` from an https page (172-174).
- A guest's joined file gets its own tab and **becomes the active tab**: `self.active = self.docs.len(); self.docs.push(ds)` (`crates/engine/src/live.rs:1188-1194`).
- `live_poll()` runs in `FigApp::ui` *before* `frame()` (`crates/ui-egui/src/lib.rs:939`). Live updates therefore keep arriving while presenting.
- `present::show` syncs from the active document on every frame (`present.rs:1633-1635`).
- `proto.present {start}` is not an edit (history=false, `crates/engine/src/cmd/proto.rs:116-122`). It accepts any frame id and resolves it with `top_level_frame` (`proto.rs:262-263`), so it works for a frame on any page.
- `open_invite(app, link)` already exists (`crates/ui-egui/src/live.rs:1036-1041`).

**What is missing for the browser viewer:**
- reading the URL;
- an Escape/Close lock ("kiosk" mode). Escape exits whatever has focus: `ctx.input(|i| i.key_pressed(Escape))` at `present.rs:1682` has no `typing` gate;
- a clipboard implementation;
- a place that hosts the web build.

**6. Whether the presenter edits the document (this matters for a view-only link)** — answered from code
- The presenter runs only two commands: `proto.settings {responsive}` (`present.rs:1680`) and `proto.present` (1826, pane only).
- All runtime state lives in the presenter's own copy (`design`/`doc`, `present.rs:259-263`, `relayout` 485-497).
- In a view-only session, the Responsive toggle is refused on the client: `check_live_access` returns `EngineError::Disabled` and rolls back (`crates/engine/src/lib.rs:864-872`). So a viewer can't use the existing Responsive option. It has to become a view-only option (state in `PresentView`) rather than a file edit.

### Part 2. The toolbar and dialog constraints, confirmed

- **Bar buttons.** The full-window bar has only the text buttons `Close, Restart, Options, Comments, Inspect` (`present.rs:2067-2083`). `BarAction` is defined at 1612-1627.
- **Editor UI is skipped while presenting.** `FigApp::frame` calls only `present::show` and `toast_ui`, then returns (`lib.rs:987-992`). `dialogs::show`, `menus::popups`, `windows::requests` and `shortcuts::handle` are never reached. A Share dialog therefore has to be drawn from `present::show`.
- **Fullscreen** exists only as the F key, using `ViewportCommand::Fullscreen(!full)` (`present.rs:1659-1662`).
- **Cmd+\\** is `view.toggleUi`, an editor-only binding (`crates/engine/src/keymap.rs:164`). The presenter has no Hide UI. egui has `Key::Backslash` (`egui-0.36.2/src/data/key.rs:41`).
- **Presenter key help rows** are at `keymap.rs:349-354`.
- **Scale options.** `PresentScale {Fit (default), FitWidth, Fill, Actual}` with labels is at `present.rs:137-191`. `PresentView` is at 195-213 and is kept in memory only.
- **Parity doc.** `docs/prototyping-parity.md:97` reads "Share a prototype link | missing".
- **Test that pins the bar height.** `present_view_tests.rs:117-140` asserts Fit zoom `796/3000`, FitWidth panRange y `2160-860`, and Actual `panRange [624,2204]`, `pan [312,0]`. These numbers come from the 40px bar and 32px padding.
- **Test hook for a centring regression test.** `Presenter::inspect()` reports `pan` as `offset(View)` (`present.rs:573, 597`). In the A1 bug state it would read `[0, y]` instead of `[range/2, y]`.

### Part 3. Contradictions and corrections between the reports

- **Line numbers are off by one or two in several places.** None of these changes a conclusion. The correct anchors are: Escape at `present.rs:1682`, F at 1659-1662, the Responsive run at 1680, `health_check` at `hub.rs:686-725`, and `open_invite` at `ui live.rs:1036-1041`.
- **Stale doc comment in figcraft-web.** `apps/figcraft-web/src/main.rs:10-13` says an https page "can only reach sessions on the same computer". The code allows `wss://` servers from https (`collab-net/src/web.rs:172`). The code is right and the doc comment is out of date.
- **Momentum stacking (S4) can't be settled by reading.** egui applies no smoothing to small Point-unit trackpad deltas (`wheel_state.rs:140-150`) and clears the deltas on the End phase (153-157). Because of the stalled-coast defect in claim 2, the coast often doesn't run at all until the next input. When it does, it runs on top of the OS momentum. The effect has to be reproduced to describe it accurately.
- **FitWidth is wrongly listed as an A1 trigger by one report.** FitWidth never has horizontal excess. Only Actual and Fill can trigger A1.

### Part 4. Still unknown

1. **Which scenario the user saw.** The code supports three left-aligned cases (A1, A2, A3), and none of them happens with the default settings. We need the user's scale, device, Responsive state and window actions.
2. **Desktop or web build.** The stalled coast (S3) and egui's line-scroll behaviour differ between platforms.
3. **Figma's exact behaviour.** This can't be answered from the code:
   - whether a top-level frame with "No scrolling" still scrolls vertically in the viewer;
   - whether Responsive keeps the designed height;
   - whether a frame without a device is clipped to its own bounds;
   - which option is Figma's default and exactly what Z toggles.
4. **Fullscreen on web.** Whether eframe's web runner honours `ViewportCommand::Fullscreen` can't be checked, because the eframe source isn't on disk; only egui-0.36.2 and epaint-0.36.2 are in the registry. From memory, and unverified, eframe's web backend has historically logged viewport commands as unhandled. Plan a `Services` hook that calls `requestFullscreen` as a fallback.
5. **Where the viewer is hosted.** No hosted figcraft-web exists and there is no `WEB_URL` constant. The share link's base URL must come from build configuration or prefs, or from a convention (`wss://host/` → `https://host/p/#…`).
6. **Live or snapshot.** A view link is live:
   - each owner edit triggers `Presenter::sync`, which resets the prototype's runtime state, transitions and flings (`present.rs:446-480`);
   - the viewer is a peer counted toward `max_people`;
   - the viewer receives the **whole file**.

   A frozen snapshot would need `NetLink::upload`, which today requires the server key. Which one to use is a product decision.
7. **Invite by email** has no backend: there are no accounts and no SMTP. At most it can be a `mailto:` through `Services::open_url`.

## Open questions
- Which left-aligned case did the user hit? All three need non-default state: A1 is Actual or Fill, then a scroll, then narrowing the window, leaving fullscreen or opening Inspect; A2 is Responsive with no device; A3 is a device narrower than the frame. With the default (Fit, no device, not responsive) the code always centres.
- Is the user on the desktop build or the web (wasm) build? The stalled wheel coast and egui's line-scroll behaviour differ between them.
- What does Figma do exactly? Does a top-level frame set to 'No scrolling' still scroll vertically in the viewer? Does Responsive keep the designed height? Is a frame with no device clipped to its own bounds? Which scaling option is the default, and what does Z toggle between?
- Does eframe 0.36.2's web runner honour ViewportCommand::Fullscreen? The eframe source isn't on disk. My unverified recollection is that the web backend ignores viewport commands, so a fullscreen button on web may need a Services hook that calls requestFullscreen.
- Where will the browser viewer be hosted, and how will the desktop app learn its base URL: a build-time constant, a preference, a wss-to-https convention, or a capability-gated HostInfo field?
- Should a shared prototype be live, using the existing view link? Then the viewer gets the whole file, counts as a peer, and its prototype state resets on every owner edit (Presenter::sync). Or should it be a frozen snapshot? NetLink::upload needs the server key today, and no request replaces an existing file's content.
- Should Responsive become a view-only option? It has to for view-only viewers, because proto.settings is refused in a view-only session (engine lib.rs:864-872).
