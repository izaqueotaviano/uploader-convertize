## FigCraft prototype player: positioning and scrolling (read-only audit)

Repo: `/tmp/claude-0/-home-user/e91b1203-da4e-5e42-9cdb-6a036b7511c0/scratchpad/figcraft`. The only commit is "Release 0.6.0", so git history has no clues. egui is 0.36.2 (Cargo.lock:1114-1115).

All player logic lives in `crates/ui-egui/src/present.rs`. Neither `crates/engine/src/cmd/view.rs` (editor canvas) nor `crates/doc` has a player-state module. The engine side holds only `proto::respond` (`crates/engine/src/cmd/proto.rs:231-244`) and the `proto.presentOptions` command (`proto.rs:135-160`). `PresentView` is defined at `present.rs:196-212`; the app keeps a copy at `lib.rs:315,424`, copies it into each new presenter at `lib.rs:689`, and writes it back at `present.rs:1677`.

### TL;DR
1. **The prototype has no real page-level scroll.** There are two separate mechanisms, and each covers only part of the job:
   - (a) A frame scrolls by itself only when its `overflow` is not `None`. The default is `None` (`crates/doc/src/proto.rs:753-755`).
   - (b) "View pan" moves a flat picture of the frame, and only when the scaled frame is bigger than the window.
   - The default scale is **Fit** (`present.rs:208-212`), which shrinks a tall landing page until it fits, so nothing is left to scroll.
   - With a device, or in Responsive mode, a tall top-level frame with `overflow=None` is simply clipped.
   - When View pan does run, fixed/sticky layers, "Scroll to" and "preserve scroll position" don't work.
2. **Two concrete ways the frame ends up on the LEFT:**
   - (A1) A stale horizontal pan offset of 0, which is stored as an absolute offset from the left edge.
   - (A2) Responsive mode stretches the frame to the window width, and content with Left constraints or Min alignment stays on the left.
3. **Five more scroll defects:**
   - Each scroll step of a frame re-renders the whole frame on the CPU, on the UI thread.
   - The wheel's coast never requests a repaint, so it starts late, when the mouse next moves, with an old speed.
   - The whole 2D wheel delta goes to one target, so a horizontal carousel swallows vertical scrolling.
   - A drag picks its scroll target without looking at the drag's direction.
   - Leaving a "while hovering" state restores the scroll offsets saved when the hover began.

### 1. How the on-screen position is computed
- **Areas.**
  - `player()` splits `rect` into a top bar of `bar_h` (40 full-window, 36 in the pane) and `area` below it (`present.rs:1959-1960`).
  - The full-window `rect` is the CentralPanel's `ui.max_rect()` (`present.rs:1652-1654`).
  - Only the optional Inspect panel (`Panel::right`, `exact_size(280)`, `present.rs:1643-1650`) reduces it.
  - The pane uses `allocate_exact_size(ui.available_size())` inside an `egui::Window` (`present.rs:1808-1819`).
- **`layout()` (`present.rs:1528-1593`):**
  - `fills = settings.responsive && device.is_none()` (1531). Responsive resizes the frame to the device screen or to the rounded `area` (1532-1533 → `respond_to` 501-508 → `relayout` 485-498 → `proto::respond` → `props::resize_node`, `crates/engine/src/cmd/props.rs:1048-1063`, which calls `apply_constraints`).
  - `fb = disp.world_bounds(current)` is the frame's own rect (`crates/doc/src/lib.rs:671-677`), not its render bounds.
  - Padding of 32 applies only to Fit and Actual when not responsive (1539). `avail = area.shrink(pad)` (1540).
  - `(sw, sh)` is the device size, or else `fb` (1541).
  - The scale factor is Fit=min(kx,ky), FitWidth=kx, Fill=max, Actual=1 (1549-1556). A device body gets a second factor pass (1560-1562). Fit is capped at 100% (1563).
  - `excess` per axis is the overflow beyond `avail`, counted only above 0.5 (1568-1569). `pan_range = excess` (1570). `p.pan` is clamped to the range unless a drag or fling is moving it (1572-1575).
  - Per axis: `along(excess, avail.min, area.center, whole, pan)`. With excess the result is `avail.min - pan`; without, it is centred (1577-1578).
  - `screen = min + body outset` (1579), and `place = Place::centered(fb, screen.center(), scale)` (1580; `Place` at 945-967).
  - The pan offset comes from `offset(View) = self.pan.unwrap_or((pan_range.0 / 2.0, 0.0))` (397). So the view is centred horizontally only while `pan` is `None`.
  - Clip: the device screen, or **the whole area** when there is no device (1590).
- `layout()` runs **twice per frame**: once before `input()` and once after (1994-1998).

### 2. Bug (a): "the prototype appears on the LEFT"
**A1. Stale horizontal pan (most likely in Actual size / Fill).**
- `pan` is an absolute offset from the left edge.
- It becomes `Some` the first time the wheel, a drag or a fling moves the View (`set_offset` 420, called from 2311, 2445 and `step_fling` 425-443).
- Whenever `pan_range.0 == 0`, the stored x is clamped to 0 (1574).
- Because `pan` is no longer `None`, the centred default at 397 never applies again.
- Once a later layout has horizontal excess, `min.x = avail.min.x - 0` (1577): the frame sits flush left and its right side is cut off.
- Ways to trigger it, after any wheel or drag on a page that fit the width:
  - opening the Inspect panel (1643-1650 shrinks `area`);
  - making the window narrower, or leaving fullscreen with F (1659-1662);
  - turning on the device body (the options menu doesn't reset `pan`; only `set_scale` 387-392, `go` 649 and `restart` 672 do);
  - a live edit that makes the frame wider (`sync` 446-483 doesn't reset `pan`).
- **Fix:** keep the horizontal pan relative to the centred position. Either store `Option<f64>` per axis (`None` = centred / top), or store a fraction (`pan.x / range.x`, default 0.5). Alternatively, re-centre x whenever `pan_range.0` changes.

**A2. Responsive with no device: the frame is stretched to the window, the content is not.**
- `respond_to(Some(whole_area))` (1532-1533) calls `respond` (`proto.rs:231-244`), which calls `resize_node` → `apply_constraints` (`props.rs:1062`).
- Children with Left constraints (Figma's default), and auto-layout frames with Min counter-axis alignment and fixed-width children, keep their x.
- In a window wider than the design, the design therefore sits at the left of a window-wide frame whose fill covers the rest.
- How often it shows depends on window width versus design width, which matches "sometimes".
- Responsive is a **file setting**: `BarAction::Responsive` → `app.run("proto.settings", …)` at 1680, menu item at 2165-2170. Once picked, it sticks for every later session.
- The same path also sets the frame's **height** to the window height (`whole_area.1`). A fixed-height landing page is squashed; content below is clipped, and scrolls only if overflow is Vertical (see S1).
- **Fix:**
  - In responsive mode change only the width; keep the designed height, and let a hug height re-hug.
  - Make Actual (100%) and centred the default.
  - Make Responsive a view option instead of a file edit.

**A3. Device narrower than the frame.**
- `viewport()` = `(min(frame.w, device.w), min(frame.h, device.h))` (1269-1273), and `fit_viewport` keeps content in place (1279-1306).
- Example: a 1440 design on "MacBook Air" (1280, `crates/doc/src/proto.rs:899-903`) or a 1920 design on "Desktop" (1440, 906-910). Only the left part shows, and the right part is reachable only with Horizontal or Both overflow.
- A frame narrower or shorter than the device is centred in the screen instead (`Place::centered`, 1580). That is not a bug, but Figma's exact behaviour should be confirmed.

**A4. Jump during transitions.**
- The outgoing frame is placed at `Place::centered(fb_from, l.screen.center(), l.scale)` (2562), which uses the new screen and ignores the old pan.
- `go()` has already reset `pan = None` (649).
- Navigating from a scrolled-down page therefore shows the old page snapping to its top, or shifting when the two frames differ in size, while the transition plays.
- **Fix:** store the outgoing `Place` in `begin()` (616-624), for example from `p.shown`, and use it as `from_place`.

**A5. No-device clip is the whole area** (1590; doc comment 1449-1451).
- Content outside a non-clipping top-level frame (off-canvas menus, decorations) draws next to the frame, so the composition looks off-centre.
- Hotspots are clipped to the area too (1427-1433).
- Figma (to verify) shows only the frame. **Fix:** clip to `screen`.

**A6. Edge case.** If `area` is narrower or shorter than 2×pad (64), `avail` becomes inverted (1540) and the scale clamps to 0.01 (1564). Tiny windows only.

**Checked and fine:**
- Centring when `pan` is `None` is exact: `avail.min - excess/2` gives the centre.
- `world_bounds` is the frame rect, not render bounds.
- Textures are placed by page coordinates (`l.place.rect(to.bounds)`, 2625).
- Nothing else takes width from the full presenter: comments use Areas (`comments.rs` ~1180), and the editor UI isn't drawn while presenting (`lib.rs:987-992`).

### 3. Bug (b): "scrolling doesn't work well"
**How the wheel is routed today (`input()`, 2238-2546):**
- The delta read is `i.smooth_scroll_delta` (2253).
- It only counts when the pointer is over `area` (2268, `over_area` from `resp.contains_pointer()` 1992-1993).
- Targets, in order: `scrollers_at()`, the innermost first (2210-2221; frames with overflow, under the pointer, with a non-zero range); then `Scroller::View` if `pan_range != 0` (2301-2304).
- The **whole 2D delta** goes to the first target that moves on either axis (2306-2316).
- Units: `1/scale` for frames, points for the View (`units_per_point` 2228-2235). Converting by zoom is correct.
- The wheel's speed is smoothed over about 50 ms (2318-2323). When the wheel delta reaches 0, a coast fling starts (2324-2329; `DECAY_WHEEL` 126, `COAST_MIN` 132).
- Drag-to-scroll: target chosen at press time (2423-2431), with rubber-band (2435-2446) and a bounce fling on release (2272-2278).
- egui already turns Shift+wheel into horizontal scrolling (`egui-0.36.2/src/input_state/wheel_state.rs:123-130`; default SHIFT at `input_state/mod.rs:117`) and Cmd/Ctrl+wheel into zoom, which the presenter ignores (`mod.rs:458-467`).
- The app overrides none of these input options; a grep for `line_scroll_speed` and similar finds nothing.

**S1. No page-level scroll for a tall top-level frame (highest impact).**
- **Default Fit** (208-212, 1552, 1563): a 1440×6000 page is drawn at about 0.15 scale and `pan_range = 0`. Nothing scrolls. The pane always fits (1536).
- **With a device, or in Responsive mode:** the top-level frame scrolls only when `overflow` is Vertical or Both (`scroll_range_in` 1158-1189, gate at 1160 and 1185-1186). The default is `None` (`doc/proto.rs:753-755`). Imported .fig files map `scrollDirection` (`format/src/fig/map.rs:954-961`), so files that rely on Figma scrolling top-level frames on its own (to verify) end up clipped with no scroll.
- **View pan (no device; Actual, FitWidth or Fill)** moves a flat texture and has these gaps:
  - fixed/sticky layers scroll away, because `apply_scroll` only handles frame scroll (1310-1335);
  - "Scroll to" never pans the View: `scroll_to_layer` walks only frames with range > 0 (535-556); without a device the top-level frame's range is 0, so `ScrollTo` returns false (789-792). Anchor links on landing pages do nothing and just flash the hotspots;
  - "preserve scroll position" ignores pan (`go` 644-649 keeps only frame scroll and resets `pan = None`);
  - `ui.set presentScroll` → `scroll_to` (558-569; `control.rs:526-533`) also touches only frame scroll.
- **Fix:**
  - Treat the presented top-level frame as an implicit vertical scroller whenever its height exceeds the visible viewport. For no device, that viewport is `(fb.w, avail.h/scale)`.
  - That means `viewport()`/`fit_viewport` and `scroll_range_in(Some(vp))` with vertical overflow implied for top-level frames.
  - Fixed/sticky layers, Scroll to, preserve-scroll and the API then all work.
  - Keep View pan only for horizontal overflow, Fill, and a device bigger than the window.

**S2. Every frame scroll step re-renders the whole frame on the UI thread.**
- `set_offset(Frame)` bumps `rev` (417).
- That rebuilds `display()` (510-524) and changes the texture key `(rev, …)` (914), so `render_node_at` runs again (921). It is tiny-skia on the CPU (`crates/render/Cargo.toml` description; `render/src/lib.rs:279-281`), synchronous, and redone for every overlay texture as well (2640).
- Phone prototypes scroll their main page this way, so wheel and drag scrolling are janky. Pan, by contrast, is cheap, because `rev` doesn't change (420).
- Related problem: tall frames at 100% on HiDPI are capped by `MAX_TEXTURE_PIXELS` and the maximum texture side (932-941), so they look blurry.
- **Fix:**
  - Render the scrolling content once, put fixed layers in a separate texture, and move the content by translating per step.
  - Or reuse the canvas's retained, off-thread renderer (`render_worker.rs:1-5`).
  - Render only the visible viewport or tiles.

**S3. The wheel coast starts late, with an old speed.**
- The fling is created at 2328 and nothing requests a repaint.
- `step_fling` asks for a repaint only while a fling already exists (1989-1991).
- egui stops repainting once `unprocessed_wheel_delta` drops to 0. The final frame of smoothing dumps the remaining amount below 1.0 (`wheel_state.rs:164-175`), and `wants_repaint_after` checks only pointer, events and unprocessed delta (`mod.rs:655-664`).
- With a mouse wheel (native, Line units), or on the web, where the trackpad has no End phase, the frame with `wheel == 0` comes only with the next input. The page then glides by itself when the mouse next moves, with the speed it had at the end of scrolling.
- Native trackpads do get a repaint, because the End event is an event.
- The test `the_wheel_coasts_after_it_stops` hides this by sending `PointerMoved` on every frame (`present_view_tests.rs:253-277`).
- **Fix:**
  - Call `ctx.request_repaint()` whenever `p.fling` is set (2277, 2328), or after `input()` while `fling.is_some()`.
  - Timestamp `p.wheel` and drop it after about 100 ms.

**S4. Momentum stacked on momentum.**
- egui already smooths Line-unit wheels (`wheel_state.rs:140-150, 161-176`), and macOS sends its own momentum events.
- The presenter adds its own coast on top.
- When the fingers lift (End clears the delta, `wheel_state.rs:153-157`), a coast starts. On the next frame `step_fling` (1989) moves it *before* `input()` lets the OS momentum cancel it (2313). The result is a jump at the handoff, plus a second glide after the OS momentum ends.
- **Fix:** coast only for Line-unit wheel input with no phases, or remove the custom wheel coast entirely.

**S5. The whole wheel delta goes to one target.**
- The loop at 2306-2316 breaks as soon as either axis moves.
- Over a horizontal carousel, a trackpad's small x jitter makes the carousel take the event, and the y component is dropped. Vertical page scrolling stalls while the pointer is over a carousel.
- **Fix:** route x and y separately (chain per axis), and lock out small cross-axis deltas.

**S6. Drag-to-scroll ignores direction.** The innermost scroller at the press point is chosen whatever the drag's direction (2424-2431). A vertical drag that starts on a carousel scrolls nothing (`rubber_band` with r=0 returns 0, 1242-1254). **Fix:** pick the innermost scroller that can move along the drag's main axis.

**S7. Hover revert puts the scroll back.**
- `fire()` saves a snapshot for OnHover and OnPress (731-737); the snapshot includes `scroll` (605-613).
- `revert()` restores it with `self.scroll = t.snap.scroll` (688).
- Scroll while the pointer rests on a "while hovering" button; when the pointer leaves, the page jumps back to where the hover began.
- **Fix:** keep the current scroll in `revert`, or leave scroll out of the snapshot.

**S8. Wheel deltas dropped.** Early `return`s before the wheel code run when a delayed trigger fires (2284-2286) or a hover reverts (2289-2293). **Fix:** handle the wheel first.

**S9. Smaller gaps:**
- With an overlay open, only the overlay's scrollers and the View take the wheel (root = overlay, 2281/2301), so a scrolling base frame can't scroll.
- The wheel over the device bezel or padding scrolls nothing (`scrollers_at` needs the pointer inside the frame, 2214-2216). Fall back to the presented frame.
- No keyboard scrolling: there is no PageUp/PageDown/Home/End/↑/↓, and Space/N step to the next frame (2516-2521).
- `display()` clones the Document on every call, twice per frame (514, 1994-1998). This is cheap-ish thanks to imbl/Arc (`doc/src/lib.rs:149,160`); low priority.
- The wheel and drag start each clone `p.doc` (2299, 2423).

**Checked and fine:**
- Shift+wheel horizontal comes from egui.
- The frame delta is converted by `1/scale`.
- Wheel scrolling clamps to the range with no overscroll (2309); a drag stretches and springs back (2435-2446, 1201-1240).
- Pan is clamped unless a drag or fling is moving it (1572-1575).
- An inner frame hands off to the View at its end (2306-2316).
