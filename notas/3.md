## FigCraft web build (`apps/figcraft-web`): what it is today and what a "view-only prototype link" needs

The repo history is one squashed commit (`833f0d2 Release 0.6.0`), so `git log` and `blame` add nothing. Everything below comes from reading the source. I modified nothing and built nothing.

### 1. What the web build is
- **It is the full editor, not a viewer.** `src/main.rs:3` says "Runs the same `figcraft_ui_egui::FigApp` as the desktop app through eframe's web runner".
  - `src/web.rs:38-44` builds `Session::new()`, installs the browser `NetLink` and calls `FigApp::new(session, Box::new(WebServices{..}))`.
  - `WebShell::ui` just forwards to `self.fig.ui(ui)` (`web.rs:65-70`).
- **It starts in one blank "Untitled" document.** `Session::new()` pushes `Document::new("Untitled")` (`crates/engine/src/lib.rs:697-701`); `Session::empty()` (`lib.rs:704`) is the variant with no documents.
- **Shared code:**
  - Dependencies are `figcraft-engine`, `figcraft-ui-egui` and `figcraft-collab-net` (`apps/figcraft-web/Cargo.toml:17-19`).
  - The UI crate has only a few wasm `cfg`s: `lib.rs:926,958` (frame timing), `present.rs:2564,2586` (timing), and `canvas.rs:519-523`, where file drops on the canvas are explicitly not supported: "Browser drops arrive asynchronously; not supported yet." → `None`.
  - In the engine, file I/O is stubbed: `crates/engine/src/cmd/file.rs:426-429` and `451-454` return "no file system in the browser".
- **What the web `Services` adds** (`web.rs:79-110`): only `open_url` (opens a new tab), `reduce_motion`, `system_language` and `gamepad_held`. Every other method keeps the trait's no-op default from `crates/ui-egui/src/lib.rs:167-210`:
  - `pick_open` and `pick_save` return `None`, so File ▸ Open and Save do nothing.
  - `save_prefs` does nothing, so preferences reset on every visit.
  - **`clipboard_set_text` is a no-op** (`lib.rs:178`), so the app's explicit **Copy link** and **Copy code** buttons (`crates/ui-egui/src/live.rs:864-869`, `online.rs:202-209`, `comments.rs:937`) silently do nothing in the browser.
  - The desktop app implements the clipboard in `apps/figcraft/src/services.rs:207-211`. The comment at `web.rs:72-73` ("the clipboard goes through egui's own web clipboard handling") only covers egui text fields.

### 2. How it is built
- **Trunk:**
  - `Trunk.toml:2-10` sets `target=index.html`, `dist=../../dist/web`, `public_url="./"`, `filehash=true`, and serves on 127.0.0.1:8767.
  - `index.html:7`: `<link data-trunk rel="rust" data-bin="figcraft-web" data-cargo-profile="web-release" data-wasm-opt="z" ... data-weak-refs />`.
  - The page is one full-screen `<canvas id="figcraft_canvas">` plus a "Loading FigCraft…" div (`index.html:20-21`).
- **Cargo profile `web-release`** (`Cargo.toml:111-118`): opt-level "s", fat LTO, codegen-units 1, strip, panic=abort.
- **eframe 0.36.2** (`Cargo.lock:1079-1080`) with features `default_fonts`, `wgpu` and `accesskit`. Rendering is WebGPU with a WebGL2 fallback.
  - Other dependencies: `wasm-bindgen 0.2`, `wasm-bindgen-futures 0.4`, and `web-sys` features Window, Document, Element, HtmlCanvasElement, Location, MediaQueryList, Navigator and Gamepad* (`apps/figcraft-web/Cargo.toml:23-28`).
  - There are no Clipboard, History, UrlSearchParams, Blob or Request features.
- **Fonts:** the wasm build embeds only Inter plus Noto Sans CJK (`crates/text/build.rs:56-70`; `release.yml:415-417`).
- **Build commands:**
  - `cd apps/figcraft-web && trunk build --release`, or `packaging/web/package.sh`, which builds and zips `dist/release/figcraft-web-<version>.zip` (`package.sh:14-17,44-55`).
  - Doc mismatch: `README.md:258` says "run `cargo xtask wasm`" for the web build. That command only runs `cargo check --target wasm32-unknown-unknown` on the crates plus the plugin builds (`xtask/src/main.rs:64-80`); it does not run trunk.
- **Size:** measured on 0.1.0 (it has not been re-measured since), from `packaging/web/README.md:10,31-36`:

| File | Raw | gzip | Brotli |
|---|---|---|---|
| wasm | 18,534,563 bytes (17.7 MiB) | 7.0 MB | 4.6 MB |
| JS glue | about 148 KB | about 22 KB | – |

  - `package.sh:27-41` fails the build if the wasm grows past 24 MiB (Cloudflare's per-file cap is 25 MiB).

### 3. How it opens files
**In practice it can't open local files.**
- No file dialog (`Services` defaults, see section 1).
- No drag-and-drop (`canvas.rs:519-523`).
- No URL parameter that loads a file.
- No fetch from a server.
- The only URL flag is `?webgl`, read with a naive substring check: `if query().contains("webgl")` (`web.rs:24`; `query()` at `web.rs:57-59`).

What does work:
- Templates, built in code (`file.newFromTemplate`, `README.md:256`).
- `file.import`, which accepts base64 `data` plus `name` (`crates/engine/src/cmd/file.rs:75-77,1107-1117`), and `file::load_bytes` (`file.rs:470-472`). This is a ready entry point if the page fetched bytes itself.
- `file.open` takes only `path` (`file.rs:656`), so it fails on wasm.
- **Joining a live session**, either with a code or with an invite link (next section).

### 4. Can it connect to figcraft-server?
**Yes, as a guest over the browser's WebSocket API.**
- `crates/collab-net/src/web.rs:1-14` says the web build "joins a session a desktop app hosts, or a file on a `figcraft-server` (also over `wss://`…)".
- The browser `NetLink` is selected in `collab-net/src/lib.rs:44-53`; its `web-sys` WebSocket dependencies are in `collab-net/Cargo.toml:31-35`.
- `join()` (`collab-net/web.rs:170-189`) parses `Invite::parse_join` and refuses a `ws://` link from an `https://` page unless it points at this machine (`web.rs:172-174`, `secure_page()` at `web.rs:138-140`).
- **What the browser cannot do:**
  - Host: `can_host` → false and `host` → Err (`web.rs:162-168`).
  - Publish, upload or share: it inherits the default `Err("publishing to a server needs the desktop app or the MCP server")` from `crates/engine/src/live.rs:465-467,502-504`. The browser therefore cannot create a share link itself; only the desktop app (or the CLI/MCP) can.
- **Default server:** `DEFAULT_SERVER = "wss://collab.craftapps.dev/"`, overridable at compile time with `FIGCRAFT_DEFAULT_SERVER` (`live.rs:61-71`), and used as `Prefs::publish_server` (`lib.rs:583,623`). Because it is `wss://`, joining by code works from an `https://` page.
- `collab.join {code | link}` is defined at `live.rs:1829-1835,1951-1954`. A joined file opens in a new tab (`live.rs:1194`), and the status becomes `Live` on `Welcome` (`live.rs:980-986`).
- **View-only access already exists:**
  - `Access::{Edit, View}` (`crates/collab/src/message.rs:59-82`).
  - The server refuses a viewer's batches (`crates/collab/src/server.rs:26,303,347`).
  - The engine limits viewers to the Move and Hand tools and reports read-only (`crates/engine/src/live.rs:831,1200,1230-1242`).
  - Online sharing creates both an edit link and a view link, each with its own code (`live.rs:177-222`; `apps/figcraft-server/src/store.rs:582-583`; `docs/server.md:74-82`).
- **Link formats** (`crates/collab-net/src/invite.rs:1-16`):
  - `figcraft://join?host=…&file=…&token=…`
  - `figcraft://join?server=wss://…&file=…&token=…`
  - `ws(s)://…/?file=…&token=…`
  - `figcraft://join?server=…&code=…`

  These are custom-scheme links, not `https://` links.
- figcraft-server does **not** serve the web build or any HTTP beyond `GET /healthz` (`collab-net/src/hub.rs:684-709`; `apps/figcraft-server/src/cli.rs:55`). `docs/server.md:7` says it is "native only (no web build)".

### 5. Does present mode work in the web build?
**Yes, as far as the code shows.** It is plain `FigApp` state drawn inside the root viewport.
- `proto.present` (`crates/engine/src/cmd/proto.rs:116-121`, `open_player` at `260-277`) requests the UI action `"present"`.
- `FigApp` turns that into `self.ui.present = Some(Presenter::new(start))` (`crates/ui-egui/src/lib.rs:686-692`).
- `FigApp::ui` draws `present::show` instead of the editor while it is set (`lib.rs:987-992`). No extra native window or viewport is involved.

Caveats:
- **Fullscreen:** the presenter's **F** key sends `egui::ViewportCommand::Fullscreen` (`present.rs:1659-1662`). Whether eframe's web runner honours that is not verified (the eframe source is not on disk here).
- **Gamepads** are wired through `WebServices::gamepad_held`.
- **Close and Escape** end the presentation and return to the editor (`present.rs:1681-1683`). A view-only link would need that blocked.

### 6. Deep links (`?join=CODE`, `#present`)
**Neither exists in the web build.**
- `web.rs` reads only `location.search()` for `webgl`, and nothing in `apps/` or `crates/` reads `location.hash` (grep finds only `web.rs:58` and `collab-net/web.rs:139`, which reads `protocol()`).
- Only the desktop app takes an invite on its command line and through the OS URL handler: `apps/figcraft/src/main.rs:150-165` calls `figcraft_ui_egui::live::open_invite(&mut fig, link)`, defined at `crates/ui-egui/src/live.rs:1034-1040`.
- `docs/prototyping-parity.md:97` lists "Share a prototype link | missing | needs multiplayer/sharing".

### 7. Deployment
**There is no hosted instance and no Pages workflow.**
- `.github/workflows/release.yml:390-434` (job `web`) installs trunk 0.21.14, runs `packaging/web/package.sh` and uploads the zip as an artifact.
- The `release` job (`release.yml:504-546`) attaches it to a draft GitHub release.
- `ci.yml:71-86` only runs a wasm32 `cargo check` through `xtask wasm`.
- There is no gh-pages, Cloudflare or Netlify deploy, and the README names no public web URL. It only says the web zip is attached to releases (`README.md:262`); the help link opens `https://getartcraft.com/apps/figcraft` (`lib.rs:719`).
- Self-hosting is documented in `packaging/web/README.md`:
  - static files, any sub-path;
  - `application/wasm` MIME type and compression;
  - HTTPS needed for WebGPU (`README.md:49-64`);
  - a sample `_headers` file;
  - an **iframe embed snippet** (`packaging/web/README.md:80-96`), which can be reused for "Get embed code".

### 8. What a "view-only prototype link" would need
Recommended path, reusing live sessions:

1. **Make the link (desktop app, "Share prototype" dialog).**
   - Publish or share the file online (`collab.share`) and take the **view** link or code (`Share.links.view`, `live.rs:215-222`; `Published.view`, `live.rs:186-187`).
   - Build an `https://` URL: `<WEB_BASE>/#view=<code-or-urlencoded-view-link>&node=<frameId>&scaling=…&hide-ui=1`.
   - Put the secret in the **fragment**, so the static host never sees or logs it.
   - Add a `WEB_BASE` constant, which does not exist today. It could mirror `DEFAULT_SERVER` (`option_env!("FIGCRAFT_WEB_URL")`) and be overridable in Preferences.
   - "Who has access: Anyone can view" corresponds to `Access::View`.
   - "Invite by email" has no backend: there are no accounts (`docs/server.md:9-10`), so at most a `mailto:` through `services.open_url`.
   - "Get embed code" can wrap the URL in the `packaging/web/README.md:82-90` iframe.
2. **Read the link (web).**
   - In `web.rs::start`, parse `location.hash` and `location.search` properly instead of `contains("webgl")`. Add the web-sys `UrlSearchParams` feature, plus `History` for `replaceState` to strip the token from the address bar.
   - For a viewer link, build `Session::empty()` rather than `Session::new()`, so no Untitled tab appears.
   - Then run `collab.join {code}` or `{link}`, the same way the desktop app calls `live::open_invite`.
3. **Kiosk present mode (ui-egui).**
   - Add a `FigApp` or `UiState` flag (for example `viewer: Option<{start, scale}>`).
   - While connecting, show a loading screen instead of the home screen or editor (`lib.rs:994-1002`).
   - Once the joined document is `Live` (`live.rs:980-986,1194`), run `proto.present {start}` (`proto.rs:260-277`). `start` accepts a numeric id or a string (`crates/engine/src/params.rs:75-81`).
   - Block Close and Escape (`present.rs:1681-1683`) and the editor fallback, so the viewer never lands in the editor.
   - Edits from the designer reach the viewer live: `Presenter::sync` copies the editor document every frame (`present.rs:3-6,1633-1635`).
4. **Copy link must work in the browser.** Implement `WebServices::clipboard_set_text` (navigator.clipboard, web-sys `Clipboard` feature) or use `ctx.copy_text` instead of the no-op default.
5. **Hosting.** Add a deploy job (GitHub Pages or Cloudflare Pages) that publishes `dist/web` over HTTPS. Viewers download the whole editor: about 4.6 MB with Brotli and about 18.5 MB raw, as measured on 0.1.0. A slimmer viewer-only build would need new feature-gating; none exists.

Alternative without a server: host a `.figcraft` file next to the site and fetch it. This needs web-sys `Request`/`Response` plus a new open-from-bytes path (`load_bytes`, `file.rs:470`, or `file.import {data}`). It is static, with no live updates and no access control.

### Side notes for the other two items
- **Scaling mapping.** `PresentScale` already has `Fit`, `FitWidth`, `Fill` and `Actual` (`present.rs:138-191`); **Z** cycles them (`present.rs:166-191`).
  - Figma "Fit width and height" = `Fit`; "Fill screen" = `Fill`.
  - "Responsive" is not a scale. It is a file setting toggled through `BarAction::Responsive`, which runs `proto.settings` (`present.rs:1613-1628,1677-1679`).
- **Left alignment (likely cause).** The view pan is stored as an absolute value.
  - `offset()` centres only while `pan == None`: `self.pan.unwrap_or((self.pan_range.0 / 2.0, 0.0))` (`present.rs:397`).
  - The first wheel scroll stores `Some((x, y))` (`present.rs:420,2302-2312`). If `pan_range.x` was 0 at that moment, x stays 0.
  - When `pan_range` later grows (window or canvas resize, the Inspect panel opening), `layout` only clamps it (`present.rs:1570-1577`).
  - The frame then sits at `avail.min.x - 0`, i.e. flush left (`present.rs:1577`).
- **Scrolling (likely cause).** The input uses egui's `smooth_scroll_delta` (`present.rs:2253`) and then adds its own coasting after the wheel stops (`present.rs:2321-2327`). On trackpads that already send momentum, this stacks two or three layers of inertia.

## Open questions
- Not verified: whether eframe 0.36.2's web runner honours egui::ViewportCommand::Fullscreen (used by the presenter's F key at present.rs:1661); the eframe source is not on disk. If it does not, the fullscreen button needs a web hook (e.g. a new Services method calling element.requestFullscreen via web-sys).
- Which public HTTPS host should serve the viewer (GitHub Pages, Cloudflare Pages, getartcraft.com)? No deploy exists today, and the share URL needs a configured base URL (no FIGCRAFT_WEB_URL-style constant exists).
- Should 'Share prototype' reuse the existing online view link and code on wss://collab.craftapps.dev (files there can expire if unopened, per Published.expires at live.rs:190), or should it be a static snapshot (fetch a hosted .figcraft file) with no live updates?
- Should the link carry a join code (short, resolved by the server) or the full view link with its token? Either way it should go in the URL fragment so the static host never logs it.
- The size numbers (18.5 MB raw / 4.6 MB Brotli) are from 0.1.0; the current 0.6.0 wasm size was not measured (building was not allowed). A viewer that downloads the whole editor may be heavy for a prototype link.
- The left-alignment and scroll diagnoses (present.rs:397/420/1570-1577 and 2253/2321-2327) are from reading the code only and have not been reproduced.
