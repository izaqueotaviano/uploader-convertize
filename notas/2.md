## Summary

`figcraft-server` is a plain-WebSocket server with no async runtime: blocking `std::net` plus `tungstenite` 0.30, two threads per connection and one hub thread. There is no axum, no tokio and no HTTP framework. It shares one TCP port (47900) between WebSocket sessions and a single HTTP route, `GET …/healthz`. It serves **no HTML, no static files and no web viewer**. A browser that opens `https://host/` gets nothing useful. All access goes through 128-bit link tokens, owner tokens or the server key, and there are no accounts. A **view-only role exists** (`Access::View`, and the server refuses a viewer's batches). There is **no "prototype-only" role** and no "share prototype" feature: `docs/prototyping-parity.md:97` lists "Share a prototype link | missing". You can build a `https://host/p/…` viewer. The simplest way is to have the reverse proxy serve the existing static `figcraft-web` build and add a small URL-to-join-to-present bootstrap in `apps/figcraft-web/src/web.rs`. This needs no server code change. Details are in section 10.

## 1. Protocol and stack

- **Crates.** `apps/figcraft-server/Cargo.toml` depends on `figcraft-collab`, `figcraft-collab-net`, `figcraft-format` (to check libraries), `figcraft-plugin` (to check plugins; it uses `wasmi`, `crates/plugin/Cargo.toml:18`), `serde`/`serde_json`, `sha2`, `crc32fast`, `toml`, `env_logger`, `ctrlc` and `rustix` (statvfs on Unix). It has no web framework.
- **Transport.** `crates/collab-net/Cargo.toml` uses "blocking tungstenite with a reader and a writer thread per connection" (`tungstenite = 0.30`, with `rustls`/`ring`/`webpki-roots` for *client* `wss://`). The hub design is described at `crates/collab-net/src/hub.rs:1-22`: "a WebSocket listener, a reader and a writer thread per connection, and one hub thread that owns a collaboration core `Server` per open file". `Hosting::serve` is at `hub.rs:457`, `accept()` at `hub.rs:748` and the per-connection `serve()` at `hub.rs:836`. Threads are spawned with `std::thread::Builder` (`hub.rs:431`).
- **Wire format.** Binary WebSocket frames only. A text frame is refused with "only binary messages are spoken here". Each frame is one version byte followed by a `postcard` body (`crates/collab/src/message.rs:714-736`). Trailing bytes are refused (`:733`), so appending fields to an existing struct breaks older peers. New features are negotiated with capability words in `client_version`, for example `SIGNALS` and `HOSTING` (`message.rs:18-39`). `PROTOCOL = 2` (`message.rs:13`).
- **Server-side TLS: none.** The server speaks plain `ws://`, and TLS comes from Caddy or nginx (`docs/server.md:370-387`).
- **Origin header is not checked.** The handshake callback only reads `X-Forwarded-For`, and only from `trusted_proxy` (`hub.rs:851-856`, `forwarded_for` at `hub.rs:729`). A page on any origin can open `wss://` to the server, and tokens still gate access.

## 2. Endpoints (all on one port, default 47900, `crates/collab-net/src/link.rs:25`)

- **HTTP.** Only a `GET` whose path ends in `/healthz` is answered, with `200 ok`. `health_check()` (`hub.rs:687-725`) *peeks* at the request line and writes a hard-coded `HTTP/1.1 200 OK … ok\n` (`hub.rs:722`). The test at `apps/figcraft-server/src/public_tests.rs:336-351` states "Anything else is a WebSocket handshake or nothing". Any other GET goes to `tungstenite::accept_hdr_with_config`, fails, is logged at debug level and the socket is closed (`hub.rs:857-864`).
- **WebSocket.** The kind of connection is chosen by its **first message** (`hub.rs:910-941`):
  - `Hello` joins a file with `{file, token}` and becomes a live session.
  - `Manage{key}` opens an admin connection using the server key.
  - `OpenLibrary` opens a team-library connection.
  - `OpenPlugins` opens the plugin directory.
  - `OpenHosting` lets a client ask about hosting, publish without the key, or manage a file with its owner token.
  - `Resolve{code}` resolves a join code.
  - Any other first message is answered "say hello first".

  Message enums are at `crates/collab/src/message.rs:586-625` (ClientMsg) and `:630+` (ServerMsg). Server-side handling is the `Backend` implementation in `apps/figcraft-server/src/store.rs:1263-1493`.

## 3. Publishing, links, join codes, owner tokens, "Your online files"

- **Publishing with the key.** This is `Admin::Publish` on a `Manage` connection, handled by `Store::publish` (`store.rs:505`). It calls `keep()` (`store.rs:545-607`), which:
  - validates the snapshot (`Replica::from_snapshot`) and the layer cap;
  - re-encodes the snapshot and checks it against `max_file_bytes`;
  - writes `snapshot.bin`, an empty `log.bin`, `links.json` and finally `meta.json`;
  - creates two links labelled "Published (edit)" and "Published (view)".

  File ids are 8 random bytes in hex and tokens are 16 random bytes in URL-safe base64 (`crates/collab-net/src/token.rs:6-17`).
- **Publishing without the key (open server).** `publish_open` (`store.rs:511-541`) applies per-IP and global caps and returns an **owner token**, stored as its SHA-256 in `meta.json` (`store.rs:584-586`). The `hosted()` handler (`store.rs:1382-1410`) lets an owner token do only `Links/CreateLink/Revoke/Rename/Code/Remove` on its own file, plus `Owned`. Ownership is checked in constant time (`store.rs:625-628`).
- **Join codes.** Nine symbols of 45 random bits. The server keeps only a hash stretched with 10,000 SHA-256 rounds, and the link token wrapped with the code (`apps/figcraft-server/src/codes.rs:1-30`). Codes are created by `set_code` (`store.rs:831`) and resolved by `resolve_code` (`store.rs:860`). Guessing limits are 10 per minute per address, a 15-minute lockout after 10 wrong codes, and 1,000 wrong codes per hour globally, which pauses codes (`apps/figcraft-server/src/abuse.rs:37-44`). Codes are documented at `docs/server.md:74-116`.
- **"Your online files"** live on the client side. The server, file id, owner token and links are kept in the app's prefs (`state.json`), with at most 200 files (`docs/server.md:118-168`). The server's only part is `Admin::Owned` (`store.rs:633-643`), which answers "what became of my files" and does not count as opening them.
- **Link formats** (`crates/collab-net/src/invite.rs:116-127`, `docs/server.md:172-184`):
  - `figcraft://join?host=<host:port>&file=<id>&token=<t>` for a plain `ws://` server;
  - `figcraft://join?server=wss://host/path/&file=…&token=…` behind TLS or under a path;
  - `ws(s)://host/?file=…&token=…`, the same link as a WebSocket URL;
  - `figcraft://join?server=…&code=…` for a code. `join_target` is at `crates/engine/src/live.rs:261-271`.

  The token is sent only inside `Hello`, never in the WebSocket request, so proxy logs never contain it (`docs/server.md:386-387`).
- **Link management from the CLI.** `figcraft-server key|files|links|plugins|reports|block-ip…` (`apps/figcraft-server/src/cli.rs:22-56`). When a server is running, these go to it over a `Manage` connection on loopback; otherwise they open the data directory directly (`cli.rs:317-327`).

## 4. Roles

- `Access::{Edit, View}` is defined at `crates/collab/src/message.rs:59-86`. A Hello is admitted with its link's access (`store.rs:1264-1269`). The core server rejects every batch from a viewer with "you can only view this file (your link is view-only)" (`crates/collab/src/server.rs:26`, `:303-307`, `:347`).
- A viewer still appears as a **peer**: it gets a `PeerJoined` and a name such as "Guest N", and it broadcasts its presence (`server.rs:296-312`, `hub.rs` Room).
- There is no "prototype-only" or "can view prototypes" role. Adding one would mean a new `Access` variant. That is a wire change, because older clients can't decode a new variant.

## 5. Team libraries and plugin directory

- **Team libraries.** `library.bin` (a `.figcraft` archive) and `usage.json` live in each file's folder. Requests are `LibraryReq::{Fetch, Publish, Usage}` (`store.rs:1454-1473`). Publishing needs an edit link. On a public server only files published with the key may hold a library (`store.rs:87`, `docs/server.md:186-218`). The browser build can't use team libraries (`docs/server.md:218`).
- **Plugin directory.** Lives in `<data>/plugins/index.json` and `<sha256>.bin` (`apps/figcraft-server/src/directory.rs:1-15`). Anyone may list and fetch; only the key may publish. Bundles are validated, never run, and hash-checked at both ends. Downloads are throttled (`store.rs:1475-1484`, `abuse.rs:28-31`, `docs/server.md:220-249`).

## 6. Default public server

- `crates/engine/src/live.rs:68-71`:
  ```rust
  pub const DEFAULT_SERVER: &str = match option_env!("FIGCRAFT_DEFAULT_SERVER") {
      Some(server) => server,
      None => "wss://collab.craftapps.dev/",
  };
  ```
- A build can override it, or leave it empty to turn online sharing off, with `FIGCRAFT_DEFAULT_SERVER` (`docs/releasing.md:54-66`).
- The terms for `collab.craftapps.dev` are in `docs/online-sharing-terms.md:3-6`: contact hello@storyteller.ai (`:15`), 30-day idle expiry (`:28-31`), not end-to-end encrypted (`:41-46`), "the code or link is the access" (`:48-52`). They contain nothing about prototype viewing or web viewing.

## 7. Auth, keys and tokens

- **Server key.** 128 bits, stored as plain text in `<data>/server.key` with owner-only permissions (`store.rs:55`, `:315-331`). It is checked with `same_secret` (constant time, `store.rs:1337-1345`). `figcraft-server key [--rotate]` prints `wss://…/?key=…` (`cli.rs:330-354`).
- **Link tokens and owner tokens.** 128 bits each, stored only as SHA-256 and compared in constant time (`store.rs:279-282`, `:797`; `docs/server.md:734-738`).
- No accounts, no email and no per-person permissions: "Not there yet: user accounts, per-person permissions, audit logs, end-to-end encryption" (`docs/server.md:778`, `apps/figcraft-server/src/lib.rs:8-9`). The server has **no email or SMTP capability**.

## 8. Storage (disk layout)

From `store.rs:4-18` and `docs/server.md:312-349`:
```
<data>/LOCK, server.json, server.key, blocked.json, reports.json
<data>/files/<id>/{meta.json, links.json, snapshot.bin, log.bin, library.bin, usage.json}
<data>/plugins/{index.json, <sha256>.bin}
```
- `snapshot.bin` is `FCSN` + generation + CRC32 + postcard state. `log.bin` is `FCLG` + checksummed journal records (`apps/figcraft-server/src/disk.rs:1-30`).
- Writes are atomic: write a temp file, then rename. The log is append-and-fsync before anyone is told of a change.
- Compaction happens after 1,000 entries, after 16 MiB of log, when the last person leaves, and on stop (`store.rs:1280-1301`, `:1311-1325`).
- Expiry: `sweep()` (`store.rs:662-676`) deletes key-less files idle for `idle_days`. It runs at startup (`store.rs:369`) and on a new connection once 10 minutes have passed since the last sweep (`store.rs:1348-1351`, `SWEEP_EVERY` at `:72`). Opening a file calls `touch` (`store.rs:1087`, `:699-707`), so viewers keep a file alive.

## 9. Limits, abuse controls, TLS, deploy

- **Configuration.** TOML or flags, defined in `apps/figcraft-server/src/config.rs:17-104`. `deny_unknown_fields` (`:18`) means any new key needs a code change. Main defaults: `max_files` 1000, `max_file_mb` 64 (16 when open), `max_connections` 512, `max_people` 256 per file, plus per-IP rates (`config.rs:74-103`).
- **Open-server transport limits.** `config.rs:279-301` sets 256 MiB queued in total, 1/8 per block, 192 MiB of reads in progress, 128 MiB in flight, and an eighth of connections reserved for sessions. Base `NetLimits` (`crates/collab-net/src/limits.rs:58-84`): 45 s idle timeout, 15 s keepalive, 100 messages/s with a burst of 400.
- **Abuse token buckets.** Per IPv4 address and per IPv6 /64, /56 and /48 (`abuse.rs:1-44`). Operators also get `block-ip`, reports and moderation commands (`docs/server.md:398-503`, with a threat-model table at `:452-473`).
- **TLS and reverse proxy.**
  - `packaging/server/Caddyfile:8-10` is just `reverse_proxy 127.0.0.1:47900`.
  - `packaging/server/nginx.conf` sets the upgrade headers and `proxy_read_timeout 120s`.
  - Set `public_url = "wss://host/"` and `trusted_proxy = "127.0.0.1"` (`docs/server.md:368-396`).
  - A path prefix works because "the server answers on any path" (`docs/server.md:384-385`).
- **`packaging/server/install.sh`** (414 lines, header at `:1-27`). It targets Debian 12+ or Ubuntu 24.04+ and:
  - installs the release binary or builds it as an unprivileged user, adding a temporary 2 GB swap file on small machines;
  - creates `/etc/figcraft-server/server.toml` and `/var/lib/figcraft-server`;
  - installs the systemd units;
  - writes `/etc/caddy/figcraft-server.caddy` and imports it from the main Caddyfile (`install.sh:328-355`);
  - sets up ufw.

  The usage is described at `docs/server.md:530-583`.
- **systemd.** `packaging/server/figcraft-server.service`: `MemoryHigh=60%`, `MemoryMax=75%`, `LimitNOFILE=4096`, `IPAddressAllow=localhost`, `ProtectSystem=strict` with only the data directory writable.
- **Docker.** `packaging/server/Dockerfile` builds on `rust:1-bookworm` and runs on `gcr.io/distroless/cc-debian12:nonroot`, with a `/data` volume and port 47900 exposed (`docs/server.md:689-715`).
- **Backups.** `figcraft-backup.timer` runs nightly, stops the server for a few seconds and keeps 7 days (`docs/server.md:351-366`).

## 10. Does it serve HTML, static files or a web viewer today? No.

- `docs/server.md:7` says the server is "headless, native only (no web build)", and the only HTTP response it ever writes is the healthz one (`hub.rs:722`).
- The web app is a separate static site. `apps/figcraft-web` is built with Trunk to `dist/web` (`apps/figcraft-web/Trunk.toml`, `public_url = "./"`), and releases ship it as `figcraft-web-<v>.zip` (`packaging/web/README.md:1-16`). "There is no server-side code."
- The wasm is 17.7 MiB raw, 6.7 MiB gzipped, 4.4 MiB with Brotli (`packaging/web/README.md:30-35`). Required headers are `application/wasm` and compression (`:52-66`). iframe embedding guidance is at `:79-96`.
- The web build **reads only `?webgl` from the URL** (`apps/figcraft-web/src/web.rs:24-28`, `:57-59`). It starts with one new document and has **no auto-join or auto-present from the URL**.
- It *can* join `wss://` sessions. It refuses `ws://` from an https page (`crates/collab-net/src/web.rs:137-140`, `:166-170`; `docs/collab-protocol.md:642-667`). It "keeps no preferences and can't publish" (`collab-protocol.md:571`), so a code join uses the compiled-in `DEFAULT_SERVER` (`live.rs:1834`).

### What a `https://host/p/…` "view prototype" page would need

**Option A (recommended, no server code change): the proxy serves the static viewer.**
1. Deploy the `figcraft-web` dist next to the server and route by matcher in Caddy:
   ```
   figcraft.example.com {
     @ws header Connection *Upgrade*
     handle @ws { reverse_proxy 127.0.0.1:47900 }
     handle /healthz { reverse_proxy 127.0.0.1:47900 }
     handle_path /p/* { root * /srv/figcraft-web; encode zstd gzip; file_server }
   }
   ```
   Today every request to `/` goes to the server (`Caddyfile:8-10`), and WebSocket clients connect to `wss://host/`, so a matcher is needed to keep both working.
2. **Client bootstrap in `apps/figcraft-web/src/web.rs`.** Parse the URL, call `collab.join {link: "wss://<page host>/?file=<id>&token=<viewToken>"}`, wait for the welcome, then run `proto.present {start?}` (`crates/engine/src/cmd/proto.rs:117-122`, `open_player` at `:260-278`; the UI handles the `"present"` request at `crates/ui-egui/src/lib.rs:686-692`). Add a kiosk or "viewer-only chrome" mode as well.
3. **URL shape.** Put the token in the **fragment**, for example `https://host/p/#<file>.<token>`, so it never reaches proxy logs or the Referer header. That keeps the property in `docs/server.md:386-387`. Derive the server from `location.host` rather than from the URL, so a crafted link can't point the viewer at another server.
4. **Avoid join codes in public URLs.** Codes have only 45 bits, and a flood of wrong ones pauses codes for everyone (`abuse.rs:37-44`). Use the 128-bit view link.
5. **Desktop "Share prototype ▸ Copy link".** Build the link from an existing **view** link: publishing creates "Published (view)" and sharing creates "Shared (view)" (`store.rs:580-581`, `docs/server.md:84-88`). Map `wss://host/` to `https://host/p/#…`. The app has no HTTP client; native networking is WebSocket only. So it either assumes the convention or the server must advertise a viewer URL. Advertising one means a new `HostInfo` field (`message.rs:426-437`), and because postcard refuses trailing bytes it must be gated by a new capability word, like `HOSTING`.
6. **Embed code.** An iframe snippet pointing at the same URL. Caddy adds no `X-Frame-Options` by default.
7. **Invite by email.** No server support exists. The practical choice is a client-side `mailto:` through `Services::open_url`. Real invites need accounts and SMTP.
8. **"Who has access: Anyone can view".** This maps to "a view link exists". Revoking it is "Stop sharing" (`docs/server.md:84-95`). Narrower access needs accounts.

**Option B: serve static files from figcraft-server itself.** Extend `health_check` (`hub.rs:687`) into a small static handler for non-Upgrade GETs, with a new config key such as `web_root` (`config.rs` uses `deny_unknown_fields`). It would need MIME types, `Content-Length`, cache headers, precompressed `.br`/`.gz`, path sanitising and a download budget. The 17.7 MiB wasm would also tie up the server's thread-per-connection slots (`max_connections` 512). Option A is simpler and safer.

**Caveats for both options:**
- Each viewer is a full live peer: its Welcome carries the whole file, it counts toward `max_people` (256 per file, `config.rs:84`) and toward `max_connections_per_ip` (32), and it shows up as "Guest N" to editors.
- With many viewers, Welcome size multiplies. For example, 30 viewers of an 8 MiB file is about 240 MiB against the 256 MiB queued budget (`config.rs:287-293`).
- A view link exposes the **whole file**, every page included, not just the prototype.
- The presenter must not send batches. Viewer batches are refused and rolled back (`crates/collab/src/server.rs:347`).

## 11. Resources and runtime dependencies (hosting advice)

- **Documented sizing.**
  - "1 CPU and 1 GB of memory are plenty for a team" (`docs/server.md:587-588`).
  - The official public server has 2 GB RAM and 2 GB swap, and the defaults hold on 1 GB (`:477-478`).
  - Recommended public setup: 2 GB RAM and a 25–50 GB disk, with backups on the same disk (`:525-528`).
  - The smallest 1 GB cloud plan is enough for `install.sh`, which adds temporary swap only for building (`:533-537`).
- **CPU.** All document logic runs on **one hub thread**, plus two lightweight threads per connection (`hub.rs:1-3`). One or two vCPUs are enough. Library and plugin checks also run on the main thread (`docs/server.md:761`).
- **Memory.** Each open file holds its document in memory, plus recent batches up to ¼ of `max_file_mb` (`config.rs:262-273`), plus send queues. systemd caps the service at 75% of RAM.
- **Disk.** The files themselves, about 2× the largest file free for compaction, at least 1 GiB free or writes are refused (`config.rs:250-252`), and about 7× the data size for nightly backups.
- **Runtime dependencies.** glibc and libgcc only: the distroless `cc` image, with no shell and no OpenSSL (`Dockerfile:77-78`). Building from source needs a C compiler for `ring` (`docs/server.md:606`). Plan for one TCP port behind Caddy (443/80), a DNS A/AAAA record, and, for the viewer, a static file host for about 5–7 MB of compressed wasm per first visit, cached forever afterwards because asset names carry a content hash.
- **Typical deployment.** A small Debian or Ubuntu VPS (2 GB RAM, 1–2 vCPU, 25–50 GB SSD) running `figcraft-server` under systemd plus Caddy, with Caddy also serving `/p/*` from the figcraft-web dist. Alternatively, the static viewer can live on Cloudflare Pages: the per-file limit is 25 MiB and the wasm is 17.7 MiB (`packaging/web/README.md:37-41`). It then connects cross-origin to the `wss://` server, which works because the server doesn't check Origin.

## Open questions
- Does the prototype presenter (crates/ui-egui present.rs) ever emit document batches (e.g. set-variable actions, interactive component state)? If so, a view-link viewer would see them refused and rolled back.
- Should a public prototype URL expose the whole file (current view links) or only the prototype? A 'prototype-only' Access variant would be a wire-protocol change.
- How should the desktop app learn the viewer URL: by convention (wss://host/ -> https://host/p/#…), or advertised by the server through a capability-gated HostInfo extension? The app has no HTTP client to probe for it.
- Will the user self-host (their own domain + FIGCRAFT_DEFAULT_SERVER build) or rely on collab.craftapps.dev, which they don't control and which serves no web viewer?
- Does the web build compiled for the viewer need FIGCRAFT_DEFAULT_SERVER set to the user's server for code-based joins? Joining by link ignores prefs.
