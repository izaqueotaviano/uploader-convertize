## FigCraft prototype player: how it works today, and where the Figma toolbar, Share and bug fixes would go

All paths are relative to `/tmp/claude-0/-home-user/e91b1203-da4e-5e42-9cdb-6a036b7511c0/scratchpad/figcraft`. The repo has a single commit (`833f0d2 Release 0.6.0`), so blame gives no history. I modified nothing and ran no cargo command.

### 1. Entering, exiting and laying out present mode

**Entering**
- The engine command `proto.present` is defined at `crates/engine/src/cmd/proto.rs:116-122`. `open_player` (`proto.rs:260-278`) picks the start frame and calls `s.request_ui("present", {start})`.
- The UI handles that request at `crates/ui-egui/src/lib.rs:686-691`: `Presenter::new(start)`, then `p.view = self.ui.present_view`.
- Ways in:
  - the `Alt+Cmd+Enter` shortcut (`crates/engine/src/keymap.rs:328`);
  - the Play button and menu in the right panel's top bar (`right.rs:94-120`);
  - the play button on a flow row (`proto_panel.rs:349`);
  - the Present button in the preview pane (`present.rs:1823-1827`);
  - a card on the home screen (`home.rs:74`).

**It takes over the window; it is not a separate window**
- At `lib.rs:987-992`, while `app.ui.present` is set, `frame()` calls `present::show(self, ui)` and `toast_ui`, then returns.
- That means none of these are drawn or run while presenting: the tab bar, the panels, `menus::popups`, `dialogs::show`, `live::*` dialogs, and `shortcuts::handle`.
- A separate prototype window is listed as missing in `docs/prototyping-parity.md:95`.
- The tab strip is skipped, so with `TitleBar::Custom` (frameless window) there are no window buttons and no drag-to-move. With `TitleBar::Inset` (macOS), the presenter bar's left content starts at x=12 (`present.rs:2119`), while the tab strip reserves 76px for the system buttons (`tabs.rs:32`).

**Exiting**
- Escape or the Close button: `present.rs:1682-1685`. The Escape check is not gated by `typing` or by an open popup.
- Automatically if the presented frame disappears (`player`, `present.rs:1966-1969`).

**Full-window structure** (`present::show`, `present.rs:1629-1686`)
- An optional right Inspect panel (`egui::Panel::right("present_inspect")`, 280px, `present.rs:1644-1651`).
- Then `CentralPanel` → `player(rect, Chrome{..FULL})` (`present.rs:1652-1654`).
- `Chrome` and `FULL` are at `present.rs:1596-1609`: `bar_h: 40.0, pad: 32.0`.
- `player()` (`present.rs:1956-2027`) splits the rect into the bar (top `bar_h`, line 1959) and the area. It paints the page background, calls `top_bar`, then `layout` (called twice per frame, lines 1994 and 1998), `input`, `draw`, and the device body and glass.

**Preview pane**
- `show_pane` (`present.rs:1783-1830`) is a floating, resizable `egui::Window` over the canvas.
- It uses the same `player()` with `Chrome{pane:true, bar_h:36, pad:12}` and always sizes as Fit (`layout`, line 1537).

### 3. Scaling modes, where they live, and what is saved

- **Enum:** `pub enum PresentScale { Fit (default), FitWidth, Fill, Actual }` at `present.rs:137-148`.
  - Ids `fit|fitWidth|fill|actual` (lines 154-161) must match `PRESENT_SCALES` in `crates/engine/src/cmd/proto.rs:247`; this is tested in `present_view_tests.rs:80`.
  - `options(device)` (line 169) leaves out FitWidth on a device.
- **Labels** (`present.rs:173-184`):
  - without a device: "Fit to window", "Fit width", "Fill window", "Actual size (100%)";
  - on a device: "Fit device to window", "Zoom device to fill window", "Device at 100%".
- **`PresentView`** (`present.rs:195-213`): `{scale, device_frame, comments, hotspot_hints, inspect}`. Its default is Fit, with the device frame and hotspot hints on.
- **Storage:** the copy is `app.ui.present_view` (`lib.rs:313-315`), written back on every frame (`present.rs:1678`). It is **in memory only**, not in prefs or the file, so it is lost when the app restarts.
  - It can be set with `proto.presentOptions {scale, deviceFrame, hotspotHints, inspect}` (`engine/src/cmd/proto.rs:134-160`), handled at `lib.rs:693-712`.
- **Responsive** is different: it is a **file** setting, `PrototypeSettings.responsive` (`crates/doc/src/proto.rs:815-818`), changed through `proto.settings` (`present.rs:1679-1681`, and `proto_panel.rs:447-452`).
- **How each mode sizes the frame** (`layout()`, `present.rs:1528-1593`):
  - the scale factor per mode is at lines 1549-1557;
  - Fit is capped at 100% (line 1563);
  - padding only applies to Fit and Actual (line 1539);
  - Responsive without a device ("fills") resizes the frame to the whole area at scale 1 (lines 1531-1533 and 1548).

### 8. The reported bugs

**(A) Prototype shown at the LEFT instead of centred**

Most likely cause: a stale horizontal pan.

1. With no pan, the view is centred horizontally (`present.rs:397`):
   ```rust
   Scroller::View => self.pan.unwrap_or((self.pan_range.0 / 2.0, 0.0))
   ```
2. A wheel or drag on the view while there is no horizontal overflow (`pan_range.0 == 0`) stores `pan = Some((0.0, y))` (`set_offset`, line 420, via the wheel at lines 2297-2322).
3. If the area later becomes narrower than the prototype, the clamp keeps x = 0 (line 1574). `along` then places the content at `min - pan` (line 1577):
   ```rust
   if excess > 0.0 { min - pan as f32 } else { centre - len / 2.0 }
   ```
   The frame's left edge lands at the window's left. Things that narrow the area: resizing the window, leaving fullscreen with F, or turning the Inspect panel on (it takes 280px, lines 1644-1651).
4. `pan` is only reset by `set_scale` (line 389), `go` (line 649) and `restart` (line 672), not when the area or `pan_range` changes.

Second candidate: Responsive without a device.
- The frame is resized to the whole player area (lines 1531-1533). Children with the default Left/Top constraints then stay on the left of a full-window-wide frame.
- Responsive is a file setting that can be turned on from the Options menu (line 2165), so after that every presentation of the page looks left-aligned.

**(B) Scrolling doesn't work well**

1. **Default is Fit.** `PresentScale::default` is Fit (lines 140-141, 208-212). A tall desktop frame without a device is shrunk to fit the window (capped at 100%), so `pan_range = (0,0)` and the wheel moves nothing unless an inner frame scrolls. Figma recommends Actual size.
2. **When a frame can scroll at all** (`scroll_range_in`, lines 1158-1189):
   - A frame with `overflow == None` never scrolls.
   - Without a device, the presented frame only scrolls children that go past its own bounds; the window-level pan comes only from FitWidth/Fill/Actual.
   - With Responsive and no device, the frame's height is forced to the window height (lines 1532-1533), so a tall page loses its height unless it hugs its content or has overflow set.
3. **Performance:** every scroll step of a frame does `rev += 1` (line 417), which causes:
   - `display()` rebuilds the document by cloning it and applying the scroll (lines 510-525; `apply_scroll` at line 1310);
   - the texture key includes `rev` (line 914), so the whole frame is re-rendered on the CPU with `figcraft_render::render_node_at` (line 921), synchronously, on every scroll or fling frame;
   - the wheel path also clones the whole `Document` on each wheel frame (`p.doc.clone()`, line 2299);
   - `layout()` runs twice per frame (lines 1994 and 1998), and each run returns another clone (`display`, line 514).

   Panning the view (`Scroller::View`) does not bump `rev`, so it is cheap. Scrolling an overflow frame, the usual case on a device or phone, is expensive and likely janky. The canvas uses an off-thread retained renderer (`render_worker.rs:1-5`); the presenter doesn't.
4. **Possible "floaty" wheel (unconfirmed):** when the wheel stops, the player starts its own fling (lines 2324-2328; `DECAY_WHEEL` 8, `COAST_MIN` 40 at lines 126 and 132). This sits on top of egui's `smooth_scroll_delta` (line 2253) and the OS's own trackpad momentum, so momentum may be applied twice.
5. **Smaller points:**
   - the wheel only works while the pointer is over the area (lines 1992-1993 and 2270);
   - drag-scrolling starts only after 6px (line 2397), and OnPress/MouseDown fire on press (line 2366), so a press on a hotspot can trigger navigation before a drag scrolls.

## Open questions
- Is the user's 'left aligned' case the stale horizontal pan (Some((0,y)) kept after the area narrows: resize, leaving fullscreen with F, opening Inspect) or Responsive-without-device (frame resized to the window, Left-constrained content)? Knowing their device/scale/responsive settings would settle it.
- Does Figma auto-scroll a top-level frame taller than the device screen when its overflow is 'No scrolling'? FigCraft does not (scroll_range_in returns 0 for Overflow::None), which could be part of the scrolling complaint.
- In Figma's Responsive mode without a device, is the frame's height forced to the window height (as FigCraft does at present.rs:1532-1533) or kept, so the page scrolls?
- Should the new scaling choice (and Hide UI) be saved to prefs? PresentView currently lives only in app.ui.present_view for the app session.
- Does ViewportCommand::Fullscreen work in the web build (eframe web)? The eframe sources were not available locally to check.
- The Share prototype dialog cannot be drawn by dialogs::show while presenting (lib.rs:987-992 returns early). Decide whether present::show draws it itself or the lib.rs present branch also calls a share dialog.
